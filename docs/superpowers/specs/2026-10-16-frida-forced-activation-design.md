# Принудительная активация скрытых HTTP-запросов через Frida — дизайн

Статус: дизайн согласован 2026-10-16, реализация не начата.
Продолжает `2026-09-28-static-backward-slice-design.md` (срез `slice.py`).

## 1. Контекст и место в пайплайне

`diff.py` даёт множество скрытых ключей `класс->метод` (есть в DEX, ни разу не вызваны
в трафике). `slice.py` на каждый такой ключ строит обратный срез: call-sites, стражи
вызова (объединение по путям), источники аргументов, UI-фронтир, `activation_cost`
(минимум реальных стражей по путям). Данный инструмент — **следующее звено**: взять
скрытый ключ и его срез и **принудительно вызвать запрос**, подтвердив факт
динамически.

Это HTTP-аналог RQ3 / Таблицы IV из ICSE 2025 (§1.5 CONTEXT.md) и реализация
перспективы №2 курсовой (§2.10): «принудительный вызов через Frida».

## 2. Цель и границы

**Главная цель (north star).** Получить **вызванный скрытый запрос с реальными
параметрами** — то есть запрос, ушедший с теми значениями аргументов, которые
приложение подставило бы само, а не с синтетическими болванками. Факт подтверждается
динамически (сетевой листенер) и сопровождается снимком фактического исходящего
запроса (метод, URL с query, тело).

**Вторичная цель (метрика RQ3).** Для каждого ключа определить **минимальную технику**,
которой он активируется с реальными параметрами, — HTTP-аналог Таблицы IV.

**В границах:** одно приложение за прогон, на стенде исследователя (Pixel XL, Android 10,
frida-server). Старт — подвыборка ~29 ключей TNT Premier с `activation_exact` (там
стоимость измерена точно и осмыслен ground truth, §4.7 CONTEXT.md).

**Вне границ v1:** иннер-retry петля LLM (one-shot на ступень), обогащение промпта
JADX-Java (старт на smali), извлечение минимального пути в `slice.py`, корректность
серверного ответа (цель — факт отправки с реальными параметрами, не 2xx).

## 3. Стратегия: многоступенчатая активация (staged)

На каждый ключ ступени пробуются по возрастанию «стоимости»; фиксируется минимальная
сработавшая. Строим снизу вверх.

- **Ступень 0 — прямой вызов Retrofit-метода.** Стражи игнорируются, аргументы берутся
  по провенанс-стратегии (§5). `call_retrofit(key, args)`. Это **проба достижимости**:
  «может ли запрос вообще сформироваться». Если удалось только с синтетическими
  аргументами — успех уровня (а), но **не** (б).
- **Ступень 1 — ближайший вызывающий + разрешение стражей.** Берётся ближайший
  call-site; глушатся реальные стражи на/ниже него; `invoke` вызывающего (suspend-aware).
  Вызывающий сам читает реальное состояние и строит аргументы → запрос уходит с
  реальными параметрами.
- **Ступень 2 — UI-фронтир + все стражи пути.** Глушатся все реальные стражи пути;
  `trigger` UI-входа (`frontier`). Best-effort: UI-контекст (View, Store) часто
  недоступен вне сцены. Провал ступени 2 — честный остаток «нужна продвинутая техника /
  эмуляция сервера».

**Двухуровневый критерий успеха:**
- **(а) достижим** — запрос ушёл (на любой ступени, параметры любые);
- **(б) активирован с реальными параметрами** — запрос ушёл с app-построенными или
  живыми значениями (не синтетическими).

Таблица IV строится по **минимальной ступени уровня (б)**. Уровень (а) отчитывается
отдельно — как «физическая достижимость» (§4.2 CONTEXT.md), не смешивается с (б).

## 4. Архитектура: фиксированный рантайм + декларативный план

Решение: **LLM выдаёт декларативный план (JSON), а не Frida-код.** Хрупкая механика
Frida написана один раз нами в `activate.js`; LLM решает только содержательную часть —
какие стражи в какие значения, что дёрнуть, откуда брать аргументы.

```
slice.jsonl ──select──> [ключ, ступень]
     │
     ▼
prompt-builder (срез + smali нужных кадров через androguard + схема + few-shot)
     │
     ▼
generate_plan(prompt)  ── OpenAI-совм. клиент ──> plan JSON (строка)
     │
     ▼
validator (schema + существование class/method/field в DEX)   ← граница доверия
     │
     ▼
Frida-сессия (spawn): hook.js [оракул] + activate.js [рантайм]
     │  script.exports.arm(plan)
     ▼
оракул: целевой ключ сработал? + снимок исходящего запроса
     │
     ▼
результат ключа → агрегат → Таблица IV + план-артефакты
```

### Файлы (ленивый минимум, переиспользование)

| Файл | Статус | Роль |
|---|---|---|
| `slice.py`, `out/<pkg>.slice.jsonl` | есть | вход |
| `hook.js` | есть, **без изменений** | baseline-оракул reached/not-reached |
| `trace.py` | есть | донор `pick_device` / spawn+attach+load |
| `activate.js` | новый | фиксированный рантайм (RPC-примитивы) |
| `activate.py` | новый | оркестратор + CLI + отчёт; внутри prompt/llm/plan |

`activate.py` плоский; дробится на модули только при >~400 строк.

## 5. Провенанс аргументов (первоклассный элемент — ради «реальных параметров»)

Порядок предпочтения источника значений для аргументов вызова и для живых объектов,
нужных триггеру:

1. **App-построенные** — прогнать реального вызывающего/вход (ступени 1–2), заглушив
   лишь минимум стражей. Приложение само читает SharedPreferences, сессию, DI-синглтоны
   и собирает аргументы. Самый достоверный источник реальных параметров.
2. **Живой инстанс из кучи** — `Java.choose(cls)` берёт существующий объект (реальный
   `Store$State`, токен, репозиторий) вместо `$new`-болванки.
3. **Снятые в трейсе** — значения, наблюдённые во время обычного исследования приложения.
4. **Синтез** — только край; результат помечается `params: "synthetic"` и в метрику (б)
   не идёт.

Источник на каждый аргумент фиксируется в результате (`arg_provenance`), чтобы в ВКР
было видно, чем именно активирован запрос.

## 6. Декларативный план (контракт LLM)

Строго JSON. Поля:

```json
{
  "key": "<fqcn>-><method>",
  "stage": 0 | 1 | 2,
  "overrides": [{"cls","method","sig","ret"}],
  "fields":    [{"cls","name","sig","value","instance"?}],
  "args":      [{"index","value"}],
  "trigger":   {"kind","cls","method","sig","suspend"?},
  "raw_js":    null,
  "rationale": "<по-русски: почему эти значения ведут к вызову>"
}
```

- `trigger.kind` ∈ `call_retrofit` (ст.0) | `invoke` (ст.1) | `trigger_entry` (ст.2).
- `value` — JSON-примитив либо кодировка объекта: `{"$new":"cls","args":[...]}`,
  `{"$choose":"cls"}` (живой инстанс), `{"$enum":"cls.FIELD"}`, `{"$null":"cls"}`.
- `raw_js` — люк подхода C: строка JS, исполняется рантаймом, если примитивов не хватает;
  по умолчанию `null`.

## 7. `activate.js` — фиксированный рантайм (device-verified)

RPC-примитивы (`rpc.exports`):

- `override_return(cls, method, sig, retval)` — хук метода, вернуть фиксированное значение.
- `set_field(cls, name, sig, value, instance?)` — статическое или по-инстансное поле.
- `choose(cls)` → handle живого инстанса (кэш по cls).
- `invoke(cls, method, sig, args, suspend)` — вызвать метод; для suspend сконструировать
  `Continuation` (или обернуть через `kotlinx.coroutines.BuildersKt.runBlocking`),
  вернуть успех/исключение.
- `call_retrofit(key, args)` — получить прокси-инстанс интерфейса (кэш из хука
  `Proxy.newProxyInstance`, как в hook.js) и вызвать метод.
- `trigger_entry(cls, method, sig, args)` — вызов UI-входа (best-effort).
- `arm(plan)` — применить `overrides`+`fields`, затем выполнить `trigger`; вернуть
  перечень исключений.
- `eval_raw(js)` — люк C.
- `capture_on(key)` — точечный снимок на целевой ключ: args на `Proxy.invoke` + итоговый
  OkHttp Request (method, url c query, тело). Отдельно от hook.js.

Коэрсия JSON→Java-значения (`$new`/`$choose`/`$enum`/`$null`) — в рантайме, один раз.

## 8. Оракул подтверждения

- **Baseline:** `hook.js` без изменений — слой 1 ловит ровно `cls->m` целевого ключа на
  `Proxy.invoke`. Появление события с целевым ключом в окне T секунд после `arm` = reached.
- **Снимок реальных параметров:** `activate.js:capture_on(key)` пишет фактический
  исходящий запрос тестируемого ключа (метод, URL+query, тело). Это и есть артефакт
  north-star-цели. По нему же судим уровень (б): параметры не пусты/не дефолтны и
  согласуются с `arg_provenance ≠ synthetic`.

Обе сессии в одном `spawn` (хук на `Proxy.newProxyInstance` обязан стоять до создания
прокси — отсюда spawn, не attach; как в trace.py).

## 9. LLM-бэкенд (плагинуемый)

Одна функция `generate_plan(prompt) -> str` поверх OpenAI-совместимого клиента. Провайдер
= `base_url` + `model` + `api_key` из env.

- **Дефолт:** OpenRouter, `deepseek/deepseek-chat-v3-0324:free` — бесплатный tier,
  программный DeepSeek, один бесплатный ключ.
- **Дропин-альтернативы:** Gemini 2.x Flash (free), Groq (free), локальный Ollama (без
  ключа/сети). Смена — только три поля конфига.
- **Бэкенд `manual`:** печатает промпт, читает вставленный JSON из файла/stdin — для
  отладки промпта без ключа.

## 10. Граница доверия (вывод LLM — недоверенные данные)

Перед тем как что-либо коснётся устройства: strict JSON parse → проверка схемы →
**проверка существования** каждого class/method/field в DEX (androguard). Не прошло →
план «невалиден» для ступени; в one-shot v1 — переход к следующей ступени, факт в лог.
Текст LLM не исполняется как код, кроме явного `raw_js`, и только на стенде исследователя
против его же приложения.

## 11. Вход и выход

**Вход:** `out/<pkg>.slice.jsonl`, APK в DEX (androguard handle), опц. список ключей для
подвыборки.

**Выход:**
- `out/<pkg>.activation.jsonl` — на ключ: `key`, `reached` (а), `activated_real` (б),
  `min_stage`, по ступеням `{stage, plan, valid, fired, exception, request_snapshot,
  arg_provenance, params}`.
- `out/<pkg>.activation.report.txt` — **Таблица IV**: распределение ключей по минимальной
  ступени уровня (б) {0 / 1 / 2 / не активирован}; отдельно — уровень (а). Качественное
  сопоставление с RQ3 ICSE 2025 с оговоркой о несопоставимости (§4.7 CONTEXT.md).

## 12. Обработка ошибок

- Нет устройства → раннер отказывает понятным сообщением; ветка prompt→plan→validate
  остаётся запускаемой офлайн (dry-run).
- Исключения Frida по каждому примитиву ловятся, возвращаются в Python, в лог.
- Невалидный план ступени не роняет прогон ключа — переход к следующей ступени.

## 13. Тестирование

Ponytail — один runnable-чек на нетривиальную логику, без устройства:
- валидатор плана: валидный / битый JSON / несуществующий член DEX;
- prompt-builder: обязательные поля присутствуют, шумовые стражи
  (`coroutine_state_machine`, `framework`) отфильтрованы;
против фикстуры-среза (реальная запись из `out/*.slice.jsonl`). `assert`-based, в `__main__`
или одном `test_*.py`. `activate.js` проверяется живым пилотом — device-verified.

## 14. Ограничения (в отчёт и в текст ВКР)

1. **Ступень 0 завышает достижимость.** Прямой вызов обходит всю логику; уровень (а) —
   верхняя оценка «в принципе формируется», не свойство реального сценария. Поэтому
   заголовочная метрика — (б), а не (а).
2. **Недетерминизм LLM.** One-shot v1 без ретраев; невалидный/неудачный план на ступени
   не повторяется. Доля активированных — нижняя оценка при данном бэкенде и промпте.
3. **Ступень 2 слаба.** Вызов UI-входа вне живой сцены часто падает — остаток уходит в
   «нужна продвинутая техника», что честно, но завышает долю неактивируемых.
4. **suspend-конструирование Continuation** — технически хрупко; часть ключей может
   падать на ступени 1 по этой причине, а не по существу стражей.
5. Один стенд, одна сборка, один регион — как в курсовой (§2.9 CONTEXT.md).

## 15. Открытые вопросы для реализации

- Формат и объём smali-контекста в промпте (сколько кадров, обрезка).
- Окно T ожидания сетевого события после `arm`.
- Политика выбора «ближайшего» call-site на ступени 1 при нескольких (минимум стражей?
  exported? по `activation_cost`-пути?).
- Критерий «параметры реальны, не дефолтны» для уровня (б) — порог/эвристика по снимку.
