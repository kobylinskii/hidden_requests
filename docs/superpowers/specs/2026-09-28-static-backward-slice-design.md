# Статический обратный срез скрытых HTTP-запросов — дизайн

Дата: 2026-09-28. Статус: реализовано, пилот прогнан (§12 — что изменилось при реализации,
что осталось открытым).
Артефакт: `slice.py` (+ `--selfcheck`), выход `out/<pkg>.slice.jsonl` и `.slice.report.txt`
(репозиторий с тех пор стал самостоятельным — пути без префикса `new/`).

## 1. Контекст и место в пайплайне

Разделяю три уровня утверждений и не смешиваю их:

- **(ICSE 2025, доказано.)** Причины недостижимости активити выведены ручным
  анализом: «обратный обход путей от `startActivity` до `onCreate` вызывающей
  активити, сбор всех условных проверок на пути» (CONTEXT.md §1.4). RQ3 (Табл. IV)
  классифицирует активити по стоимости активации: тривиально 22.7%, +данные 24.3%,
  +разрешение стражей 47.6%.
- **(Курсовая, показано.)** Пайплайн статика−динамика на 5 приложениях: 671/1106
  запросов (~61%) скрыты. Классификация скрытых — эвристиками по URL, ошибка ~10%.
  Оценка на будущее: **~40% NOT FOUND имеют 1–2 простых условия вызова**.
- **(Диплом, планируется — данный этап.)** Заменить эвристики по URL анализом
  условий вызова в байткоде. Этот документ описывает **обратный срез**: для каждого
  скрытого запроса восстановить call-sites и **стражи на пути** (HTTP-аналог
  «условных проверок на пути» из ICSE). Срез — вход для следующего этапа
  (классификация в аналог Таблицы IV) и для этапа принудительного вызова (Frida).

Срез стыкуется с уже готовым `new/diff.py`: тот выдаёт `hidden.jsonl` с ключами
`класс->метод`; слайсер берёт эти ключи и APK той же сборки.

## 2. Цель и границы

**Делает:** для каждого скрытого ключа `Class->method` находит места вызова в
байткоде, обратным межпроцедурным обходом собирает управляющие стражи и
происхождение аргументов, пишет структурированный срез.

**Не делает (осознанно вне объёма этого этапа):**
- Не классифицирует в категории Таблицы IV — это следующий этап, потребляющий
  `slice.jsonl`. Срез даёт сырьё (число и тип стражей), не вердикт.
- Не решает удовлетворимость стражей и не эмулирует сервер.
- Не выполняет полный контекст-чувствительный IFDS по всему приложению (см. §11).

## 3. Инструмент и архитектура: гибрид

Зафиксировано с заказчиком: **androguard + networkx** (оба уже в `new/.venv`:
`androguard==4.1.4`, `networkx==3.7`). Soot/FlowDroid — **в резерве** (§11).

Обоснование против Soot/FlowDroid на старте: APK 136 МБ multi-dex — реальный риск
таймаута/OOM у whole-app FlowDroid; FlowDroid — forward-taint, обратный срез из
коробки не делает; androguard уже даёт XREF, CFG и инструкции по регистрам.
Контекст-чувствительность достигается **сужением путей** (обратный под-граф от
каждого call-site), а не полным IFDS-движком.

Гибрид = дешёвое глобальное сужение (стадия A) + точный локальный анализ на малом
под-срезе (стадия B).

### Стадия A — androguard, по всему APK, дёшево

APK грузится один раз (`AnalyzeAPK`, ~130 с на пилоте) на все ключи.

1. **Резолв call-sites.** Для ключа `Class->method` беру `MethodAnalysis`
   интерфейсного метода (`dx.find_methods`, `no_external=False`), затем
   `get_xref_from()` → множество (вызывающий метод, offset). Retrofit-вызов
   компилируется в `invoke-interface` на интерфейс, XREF ловит тот же ключ, что
   BFScan/`hook.js`. **Проба подтвердила: 12/12 пилотных ключей дали ≥1 call-site.**
2. **Обратный межпроцедурный граф.** От каждого call-site — BFS вверх по
   `xref_from`, узлы = методы, рёбра = «вызывает» (networkx `DiGraph`). Обход
   останавливается на фронтире (§5.4). Объединение методов на путях = под-срез
   этого ключа. Под-срез мал относительно всего APK.

### Стадия B — точный анализ только на под-срезе

Для каждого семантического кадра под-среза считаю в Python+networkx управляющие
зависимости (§5.5) и мелкий def-use (§5.6–5.7). Soot не задействуется.

## 4. Вход и выход

Вход:
- `--hidden out/<pkg>.hidden.jsonl` — выход `diff.py`; берутся записи `status=hidden`.
- `--apk apk/<pkg>.apk` — та же сборка, что снята для статики/динамики.
- `--out out/<pkg>.slice.jsonl`.

Версия сборки: слайсер читает `meta` из `hidden.jsonl`/`dynamic.jsonl` если есть и
дублирует в шапку отчёта — как `diff.py`, чтобы срез нельзя было спутать с другой
сборкой.

Выход `slice.jsonl`, одна запись на ключ:

```json
{
  "key": "gpm...DownloadsApi->disallowDeviceDownload",
  "cls": "gpm...DownloadsApi",
  "method": "disallowDeviceDownload",
  "reached": true,
  "call_sites": [{"caller": "gpm...DownloadsApiRepository->disallowDeviceDownload", "offset": 194}],
  "guards": [
    {"frame": "one...SomeViewModel->onClick",
     "opcode": "if-eqz",
     "sense": "true_branch_calls",
     "operand": {"source_kind": "invoke", "source_name": "one...SessionManager->isLoggedIn", "descriptor": "()Z"}}
  ],
  "guard_count": 1,
  "args": [{"index": 0, "source_kind": "param", "note": "propagated from caller"}],
  "frontier": "androidx...Fragment->onViewCreated",
  "depth": 3,
  "plumbing_skipped": ["postDeviceUpdate$default", "invokeSuspend"],
  "inconclusive": false,
  "notes": []
}
```

Смысл полей:
- `reached=false` — XREF пуст: вызов только через рефлексию или мёртвый код ⇒
  категория *No caller*. Полезный самостоятельный результат.
- `guards[]` — управляющие стражи на пути; `sense` — какая ветвь ведёт к вызову.
- `operand.source_kind` ∈ `const|field|invoke|param|unknown` (§5.6).
- `args[]` — происхождение фактических аргументов скрытого вызова (§5.7), ось
  «нужны данные».
- `inconclusive=true` — путь не построен/не разрешён (обфускация, взрыв путей,
  ветвь через рефлексию). Честно отделяется от «стражей нет».

## 5. Механика

### 5.1 Резолв call-sites
`dx.find_methods(classname=^L<slashed>;$, methodname=^<name>$, no_external=False)`,
затем `get_xref_from()`. Класснейм экранируется (`re.escape`) и якорится — API
принимает regex. Перегрузки не различаются (как в `diff.py`): все call-sites
любой перегрузки учитываются под одним ключом.

### 5.2 Обратный межпроцедурный граф
BFS вверх от каждого call-site. Каждый посещённый метод → `xref_from` даёт его
вызывающих. Дубли гасятся посещённым множеством (метод анализируется один раз).
Циклы (рекурсия/корутины) обрезаются посещённым множеством. Стоп — по фронтиру §5.4.

### 5.3 Прозрачный проход плумбинга
Проба показала, что call-sites сидят в Kotlin-машинерии, которая не несёт
семантических стражей и должна проходиться насквозь (не считаться за кадр и не
тратить лимит глубины). Плумбинг-кадр детектируется по:
- имя оканчивается на `$default` (бридж дефолтных аргументов);
- имя `access$...` (синтетический аксессор);
- объявляющий класс содержит `$$inlined$` или `$$special$`;
- метод `invokeSuspend`/`create`/`invoke` класса-континуации (суперкласс
  `kotlin.coroutines.jvm.internal.BaseContinuationImpl`/`SuspendLambda`).

Плумбинг-кадры пишутся в `plumbing_skipped` для прозрачности, но стражи в них не
собираются (кроме структурных ветвлений стейт-машины корутины — они помечаются
`notes:["coroutine_state_machine"]` и учёт их идёт с флагом низкой уверенности,
не как настоящий страж).

### 5.4 Фронтир и лимит
Стоп обхода вверх при любом из:
- вызывающий — UI/lifecycle/entry-колбэк (`onCreate/onStart/onResume/onClick/
  onViewCreated/...`, `androidx.*`/`android.*` фреймворк, exported-компонент из
  манифеста) — семантическая граница, аналог `onCreate` в ICSE;
- достигнут лимит **N=6 семантических кадров** (плумбинг не считается) — страховка
  от взрыва путей; при срабатывании `notes:["depth_cap"]`;
- у метода нет вызывающих (`xref_from` пуст) — это и есть точка входа/фронтир.

### 5.5 Управляющие зависимости (стражи)
Критерий среза в кадре — базовый блок с нужным invoke (скрытого метода или
следующего callee к нему). Стражи = ветвления `if-*`, от которых блок транзитивно
control-dependent, по Ferrante–Ottenstein–Warren:
1. CFG кадра из базовых блоков androguard (`method.get_basic_blocks()`), + виртуальный
   выход, соединённый со всеми терминальными блоками.
2. Пост-доминаторы = доминаторы на реверснутом CFG с корнем-выходом
   (`networkx.immediate_dominators`).
3. Для ребра ветвления (A→B), где B не пост-доминирует A: идём вверх по дереву
   пост-доминаторов от блока-критерия до `ipdom(A)`, помечая control-dependence на A.
Каждый такой A даёт одного стража; `sense` = какая из веток A ведёт к критерию.

### 5.6 Извлечение стража
Для блока-ветвления A: opcode сравнения (`if-eqz/if-nez/if-eq/if-ne/if-lt/...`) и
регистры-операнды. По каждому операнду — **мелкий** backward def-use внутри кадра
(последнее определение до использования, вверх по блоку и непосредственным
предшественникам):
- `const*` → `source_kind=const`, значение;
- `iget*/sget*` → `field`, `fqcn.name` (фича-флаг/auth/конфиг);
- `move-result` после `invoke*` → `invoke`, сигнатура callee (напр. `isLoggedIn()Z`);
- регистр-параметр `pN` → `param`, индекс; при межпроцедурном обходе индекс
  протаскивается на кадр выше (сопоставление факт. аргумента в call-site);
- иначе → `unknown`.
Глубина def-use — один семантический хоп (потолок, §9).

### 5.7 Происхождение аргументов
Для фактических аргументов скрытого вызова — тот же классификатор источника, что
и в §5.6, по регистрам аргументов в call-site. Кормит ось «нужны данные» будущей
классификации.

## 6. Компоненты и границы

Один модуль `new/slice.py`, чистые функции с явными зависимостями (тестируемы без APK):

- `load_hidden(path) -> list[key]` — читает `hidden.jsonl`.
- `resolve_call_sites(dx, key) -> list[CallSite]` — §5.1 (нужен androguard).
- `backward_frames(dx, call_site, limit) -> list[Frame]` — §5.2–5.4 (androguard+networkx).
- `control_deps(cfg, criterion) -> list[BranchBlock]` — §5.5, **чистая** (граф на вход).
- `classify_operand(method, reg, at) -> Operand` — §5.6, def-use.
- `slice_key(dx, key) -> dict` — сборка записи выхода.
- `report(records, meta) -> str` — человекочитаемый отчёт (§7).
- `main()` / `_selfcheck()` — как в `diff.py`.

Граница: андроид-специфика (androguard) изолирована в резолве/обходе;
алгоритмика (`control_deps`, дерево пост-доминаторов) работает на абстрактном
графе и тестируется синтетикой (§10).

## 7. Отчёт `.slice.report.txt`
Шапка: пакет + версия сборки. Тело:
- сводка: всего ключей, `reached` / `no_caller`, `inconclusive`;
- **распределение `guard_count`** (0,1,2,3,4+) — прямое сырьё для аналога Таблицы IV;
- топ источников стражей (какие поля/методы чаще всего гейтят запросы);
- построчно на ключ: call-sites, стражи, аргументы, фронтир.

## 8. Ground truth и валидация (RQ2)
Метрика без валидации не годится (бриф §«если предлагаешь эксперимент — сразу
ground truth»).
- Случайная подвыборка 15–20 из 133 ключей (фиксировать seed).
- Ручной разбор в JADX: истинные стражи на пути до фронтира.
- Сравнение с выходом слайсера → precision/recall детекции стражей; отдельно —
  доля `reached`/`inconclusive` против ручной оценки.
- Явно задокументировать классы ошибок: suspend-стейт-машины, DI/Hilt-развязка
  вызывающих, рефлексия, точечная обфускация (`nskobfuscated.*`).

## 9. Ограничения (в отчёт и в текст ВКР)
- Def-use глубиной один хоп: цепочка `x = a; if (a>b)` разрешится, длинная
  трансформация операнда — `unknown`. Потолок; углубляется при необходимости.
- Перегрузки не различаются (ключ `cls->method`, как весь пайплайн).
- DI/Hilt может уводить вызывающих через сгенерированный код — помечается `notes`.
- suspend-стражи внутри стейт-машины — низкая уверенность, отдельный флаг.
- Рефлексивные call-sites не видны XREF ⇒ `reached=false` (корректно = *No caller*).
- `reached=false`/`inconclusive` ≠ «невозможно вызвать» — только «статически не
  разрешено в этих рамках».

## 10. Тестирование
`python3 slice.py --selfcheck` (паттерн `diff.py`): `assert`-проверки на
**синтетических CFG**, собранных вручную (networkx-граф + разметка ветвлений), с
заранее известными ожидаемыми стражами — изолируют нетривиальную логику
(control-dependence, дерево пост-доминаторов, классификатор источника). Ромб
if/else, вложенные if, цикл, ранний return. Андроид-I/O не юнит-тестируется —
его проверяет ground-truth §8. Без фреймворков и фикстур.

## 11. Отложено: когда подключать Soot
Триггер — если валидация §8 покажет систематическую нехватку androguard-анализа
(напр. стражи через длинные межпроцедурные data-цепочки, неразрешимые мелким
def-use). Тогда Soot/SootUp подключается **точечно на под-срезе** (крошечная доля
APK ⇒ трактуемо), не whole-app. До этого момента — YAGNI.

## Открытые вопросы для реализации
- Формат `CallSite`/`Frame`/`Operand` — dataclass или dict; склоняюсь к dict ради
  единообразия с `diff.py` и прямой сериализации.
- Кэш загруженного `dx` между прогонами (pickle) — только если 130 с загрузки
  станут мешать итерациям; пока не нужно.

## 12. Статус реализации (постфактум, после пилота)

Реализовано по плану `docs/superpowers/plans/2026-09-28-static-backward-slice.md`
(7 задач, subagent-driven, с ревью каждой задачи и финальным ревью всей ветки).
Открытые вопросы выше закрыты: формат записи — dict (§4), кэш `dx` не понадобился —
слайсер грузит APK один раз на весь список ключей.

**Отклонения от исходного дизайна, принятые по ходу реализации** (полный список
решений с обоснованием — в git-истории коммитов `slice.py`):
- **§5.4, лимит глубины.** Зафиксирован как **per-path**, а не глобальный кап на
  суммарное число кадров: глобальный кап на реальном методе с fan-in давал недосчёт
  кадров и стражей (11 кадров обрезались до 6) — занижал бы `guard_count` именно
  там, где стражей больше всего.
- **§5.3, корутинная машинерия.** Кроме `coroutine_state_machine`, добавлен второй
  фильтр — **`framework`**: стражи на `android.*`/`androidx.*`/`java.*`/`kotlin.*` и
  компиляторных проверках (`Intrinsics.areEqual`, `Enum->ordinal`). Без него топ
  источников стражей в отчёте был забит UI-обходом (`ViewGroup.getChildAt` и т.п.),
  а не условиями активации приложения.
- **§5.7, args.** Реализовано (классификация источника аргументов вызова по тому же
  классификатору, что и стражи) — в исходном плане реализации этот пункт провалился
  в шов между задачами и был обнаружен и закрыт на финальном ревью ветки.
- **§11, Soot.** Триггер подключения не сработал — вся реализация на androguard+networkx.

**Пилот на TNT Premier прогнан** — числа и четыре открытых методологических вопроса
(объединение стражей вместо минимума по путям; слабый детектор фронтира на
обфусцированном APK; недоразбор второго операнда двухрегистровых сравнений;
ground truth §8 не прогнан) — `CONTEXT.md` §4.7 и `README.md` (раздел «Часть 2»).
Эти вопросы **не закрыты кодом** — это открытые решения по методологии метрики,
оставленные на решение автора работы, не инженерные баги.
