# Сканер HTTP-объявлений в Docker

Контейнер выполняет статический анализ и сравнение с наблюдениями. Для новой
трассы Android и `frida-server` 17.23.3 работают на хосте или в Genymotion.

## Сборка и запуск

Для сборки нужны wheel Frida 17.23.3 в корне проекта и
`BFScan/target/BFScan-3.1.4.jar`. После правок в JS пересоберите агенты.

```bash
./build-agents.sh
docker build -t hidden-scanner .
docker run --rm -it --network host \
  -v "$PWD/apk:/work/apk:ro" -v "$PWD/out:/work/out" \
  -e ADB_DEVICE=127.0.0.1:6562 \
  hidden-scanner /work/apk/demo.apk
```

В эмуляторе исследуйте приложение обычными действиями. Завершите сбор трассы
через Ctrl-C. Для анализа готовых артефактов передайте `STATIC_IN` и
`DYNAMIC_IN` с путями внутри контейнера. Устройство для этого запуска
не требуется. Если передан только `DYNAMIC_IN`, BFScan построит новый каталог.

BFScan и трассировщик можно запускать независимо через `bfscan.sh` и
`trace.py`. Каталог нужно переносить вместе с файлом `*.meta.json`.
Идентификатор сборки — SHA-256 APK. Для динамики хеш берётся у установленного
base APK. Для split-установки сканер проверяет дополнительные APK и записывает
их SHA-256 в `installed_apks`. Конфигурационные splits без DEX поддерживаются.
Если split содержит DEX, требуется статический анализ этого дополнительного
кода; текущий прогон получает `partial`. Ошибка чтения APK или изменение
состава установки также приводят к `partial`. Причины печатаются в терминале
и сохраняются в завершающей записи трассы. Версия пакета сама по себе недостаточна.

| Переменная | Назначение |
|---|---|
| `ADB_DEVICE` | ADB-адрес Android-устройства для новой трассы |
| `OUT_DIR` | Каталог результатов. Значение по умолчанию — `/work/out` |
| `STATIC_IN`, `DYNAMIC_IN` | Каталог BFScan и трасса той же сборки |
| `TRACE_APPEND=1` | Дописать сеанс в завершённую трассу той же сборки |
| `HIDDEN_IN` | Продолжить с нового `*.hidden.jsonl` с файлом `*.meta.json` |
| `REASONS_IN` | Повторно использовать метрики стражей той же сборки и набора скрытых объявлений. Рядом нужен файл `*.meta.json` |

При изменении исходников пересоберите тег `hidden-scanner` из корня этой рабочей копии.
Для повторного анализа по сохранённому списку достаточно локальных файлов:

```bash
docker build -t hidden-scanner .
docker run --rm --network none \
  -v "$PWD/apk:/work/apk:ro" -v "$PWD/out:/work/out" \
  -e HIDDEN_IN=/work/out/premier-run/gpm.tnt_premier.hidden.jsonl \
  -e OUT_DIR=/work/out/premier-replay \
  hidden-scanner /work/apk/gpm.tnt_premier-2.134.0.apk
```

## Артефакты

| Файл | Содержимое |
|---|---|
| `<pkg>_methods.md` | Каталог BFScan с примерами. В `*.meta.json` записаны хеши APK и каталога и статус сбора |
| `<pkg>.dynamic.jsonl` | Сеансы трассировки с идентификатором сборки и завершающим статусом. Размечены вызов метода, создание OkHttp-вызова, создание объекта ответа и открытие URL-соединения |
| `<pkg>.hidden.jsonl` | Одна строка на объявление BFScan. Статусы `observed`, `not_observed`, `insufficient_data` |
| `<pkg>.bodies.jsonl` | Одна запись на скрытое объявление. Поле `body` содержит текст тела BFScan либо `null` при отсутствии примера |
| `<pkg>.request-slice.jsonl` | Одна запись на скрытое объявление. Для каждого прямого места вызова сохраняются смещение, типы аргументов и графы происхождения значений |
| `<pkg>.reasons.jsonl` | Метрики стражей для каждого скрытого объявления, `activation_cost`, `activation_exact`, причины остановки в `notes`. Контрольная сумма, сборка и статус сохраняются в `*.meta.json` |
| `<pkg>.reasons.report.txt` | Версия APK, статистика по объявлениям, списки точных, нижних и неопределённых оценок |

При неполной трассе точные положительные наблюдения той же сборки сохраняются.
Отсутствие вызова классифицируется как `not_observed` только при завершённых
артефактах и подтверждённом покрытии интерфейса Retrofit. Событие создания
объекта ответа может относиться к кэшу или промежуточному ответу.

Сканер печатает метод, маршрут, ключ и тело каждого объявления со статусом
`not_observed`. JSON, формы и multipart выводятся в формате каталога BFScan.
При отсутствии примера сканер печатает «в BFScan нет примера тела» и сохраняет
статус `no_bfscan_example`. Литерал JSON `null` сохраняется как строка `"null"`
со статусом `example`. Результаты отражают шаблоны статического анализатора.

Срезы и отчёт BFScan связываются по `build` и `declaration_id`. Индексы аргументов начинаются с нуля; служебный завершающий Kotlin Continuation пропускается. Для объявления без найденного прямого вызова записывается `no_direct_call_sites`. Статус `analyzed` означает, что места вызова обработаны; в графе могут остаться неизвестные значения.


Во время обработки сканер показывает текущий этап и время работы каждые 10 секунд.
После сравнения выводятся общее количество статических объявлений, число уникальных
ключей, количества и доли наблюдавшихся, скрытых и неопределённых объявлений.
Для скрытых показаны HTTP-методы и наличие примера тела BFScan. При построении
срезов выводятся счётчик объявлений, результат и число мест вызова; в конце
печатается общая сводка. Статистика идёт в stderr, тела запросов — в stdout.
Новые JSONL-отчёты и метаданные создаются с правами 644 для чтения на хосте.

Сборка агента активации находится в `archivive/build/activate.js`.

BFScan начинает с целого APK. Запасной анализ отдельных DEX при нехватке
памяти помечается `partial`. Подтверждённый вызов метода Retrofit, создание
HTTP-запроса и создание ответа представляют разные наблюдения. Повторный
запуск проверяет тип входного отчёта и DEX-дескрипторы. Отчёты одного запуска
имеют общий `run_id` в метаданных; контрольные суммы собраны в `<pkg>.run.json`.
Чтобы перенести комплект целиком, копируйте выходной каталог вместе со скрытым
каталогом поколений. Для отдельных JSONL и метаданных используйте `cp -L`.
